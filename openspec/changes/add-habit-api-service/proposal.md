# Proposal

## Why

Учебное задание: показать spec-first разработку на маленьком сервисе. Контракт `api.yaml`
(OpenAPI 3.0) должен быть единственным источником истины, а серверный каркас — генерироваться
из него, а не писаться руками. Дополнительно нужен пример того, как OpenSpec фиксирует
поведение до кода: сначала спека, потом генерация, потом рукописный слой.

## What Changes

- Новый `api.yaml` (OpenAPI 3.0) — трекер привычек: `GET /habits`, `GET /habits/{habitId}`,
  `POST /habits`, `PUT /habits/{habitId}`, `DELETE /habits/{habitId}`; схемы `Habit`,
  `HabitInput`, `HabitListResponse`, `Error`; `securitySchemes` — HTTP Bearer; ответы
  200/401/403/404.
- Генерация каркаса в `service/` командой
  `npx @openapitools/openapi-generator-cli generate -i api.yaml -g spring -o service`.
  Сгенерированные пакеты (`api/`, `model/`) не редактируются.
- Рукописный слой в пакете `service`: хранилище в памяти и реализация сгенерированных
  интерфейсов, статическая проверка Bearer-токена.
- Сборка сервиса через Maven (`mvn -q package`).
- `README.md`: как получены спека и каркас, что написано руками, что сгенерировано, что
  осталось заглушкой.

Вне области: база данных, настоящая аутентификация и авторизация, Docker, деплой, тесты.

## Capabilities

### New Capabilities

- `habits`: жизненный цикл привычки через HTTP — список с фильтром по активности, чтение по
  идентификатору, создание, обновление, удаление; семантика «не найдено» и владения записью.
- `api-auth`: проверка Bearer-токена на всех эндпоинтах `/habits` — отказ при отсутствующем или
  неверном токене и при обращении к чужой привычке.

### Modified Capabilities

Нет: в проекте пока нет ни одной спеки, все требования новые.

## Impact

- Новые файлы в корне репозитория: `api.yaml`, `README.md`, каталог `service/`.
- Внешние зависимости: `openapi-generator-cli` (через `npx`), Maven, JDK для сборки.
- Правок существующего кода нет — репозиторий `hw09` содержит только `AGENTS.md` и `openspec/`.
- Риск окружения: в текущей среде нет Maven, а из JDK доступны только Java 8 (JRE) и JDK 16.
  Проверка `mvn package` требует отдельного решения — вынести в задачи как блокирующий пункт.
