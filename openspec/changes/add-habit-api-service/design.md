# Design

## Context

Репозиторий `hw09` пуст по коду: есть только `AGENTS.md` и `openspec/`. Мотивация — в
`proposal.md`, требования — в `specs/habits/spec.md` и `specs/api-auth/spec.md`.

Ограничения окружения, влияющие на решения:

- Maven не установлен, `mvn` не найден в `PATH`.
- Из JDK доступны только Oracle JRE 1.8 (без `javac`) и JDK 16 в `~/.jdks/openjdk-16.0.1`.
- `node`/`npx` есть, значит `openapi-generator-cli` запускается через `npx`.
- Docker отсутствует — контейнеризация вне области.

## Goals / Non-Goals

**Goals:**

- Контракт `api.yaml` полностью описывает API: пять операций, четыре схемы, Bearer security.
- Каркас Spring Boot целиком получен генератором; рукописный код не пересекается с
  генерируемыми пакетами и переживает повторный `generate`.
- Поведение из спек реализуется поверх сгенерированных интерфейсов без правки последних.

**Non-Goals:**

- Хранение между перезапусками, БД, миграции.
- Настоящая аутентификация: выдача, срок жизни, отзыв токенов, роли.
- Тесты, CI, Docker, деплой.

## Decisions

### D1. Модель данных и идентификаторы

`Habit`: `id` (string, `uuid`, readOnly), `title` (string, 1..120), `description`
(string, ≤500), `active` (boolean), `ownerId` (string, readOnly), `createdAt`/`updatedAt`
(`date-time`, readOnly). `HabitInput`: `title` (required), `description`, `active`
(по умолчанию `true`). `HabitListResponse`: `items` (array `Habit`) + `total` (integer).
`Error`: `status` (integer), `message` (string).

`Error` использует `status`, а не `code`, чтобы не путать HTTP-код с прикладным.

Альтернатива «числовой `id`» отклонена: UUID не требует счётчика и переживает перезапуск без
коллизий в сид-данных, которые заданы константами.

### D2. Коды ответов

Следуем заданию буквально: `200` на всех успешных операциях (включая `POST` и `DELETE`),
`401`, `403`, `404` для ошибок. `POST` возвращает `200` с созданной сущностью, а не `201`;
`DELETE` возвращает `200` без тела, а не `204`.

Следствие: код `400` в контракте отсутствует, валидация входа объявлена декларативно
(`required`, `maxLength`, `minLength`) и остаётся на усмотрение Spring (по умолчанию вернёт
`400`). Это осознанное расхождение с типовой практикой; спека его не требует и не запрещает.
Причина: задание фиксирует набор кодов, лишние коды усложнили бы проверку.

### D3. Владение и `403`

`ownerId` — readOnly-поле `Habit`, заполняется сервисом из токена. Токен → владелец
разрешается статической картой: `demo-token` → `demo-user`, `other-token` → `other-user`.

Хранилище при старте заполняется двумя привычками с фиксированными `id`: одна принадлежит
`demo-user`, вторая — `other-user`. Это делает `403` проверяемым вручную и не требует
дополнительного кода для создания чужой записи.

Альтернатива «хранилище без владельца» отклонена: тогда `403` из спецификации нечем
продемонстрировать. Альтернатива «`404` вместо `403` для чужих привычек» отклонена: спека
`api-auth` требует `403`, чтобы факт владения был наблюдаемым.

### D4. Рукописный слой

Три класса в пакете `…service`, не в генерируемых пакетах:

- `HabitStore` — `ConcurrentHashMap<String, Habit>` и сид-данные, без знания о HTTP.
- `HabitService` — операции над хранилищем с проверкой владения; бросает доменные исключения.
- `HabitController` — `@RestController`, реализует сгенерированный интерфейс `HabitsApi`,
  переводит доменный результат в `ResponseEntity`.

Доменные исключения: `HabitNotFound` → `404`, `HabitForbidden` → `403`; обрабатываются одним
`@RestControllerAdvice`, который собирает `Error`.

Альтернатива «генерировать с `interfaceOnly` и писать контроллер с нуля» отклонена: задание
требует каркас генератора по умолчанию, а не кастомную конфигурацию.

### D5. Аутентификация

`OncePerRequestFilter` + `WebMvcConfigurer` в рукописном пакете:

- путь начинается с `/habits` → разобрать `Authorization`;
- нет заголовка, схема не `Bearer`, токен неизвестен → `401` с телом `Error` (JSON пишется
  через `ObjectMapper`);
- иначе положить `ownerId` в атрибут запроса, контроллер читает его оттуда.

Альтернатива «проверка внутри каждого метода контроллера» отклонена: дублирование и риск
пропустить операцию. Альтернатива «Spring Security» отклонена как избыточная для демонстрации.

Генерируемый `securitySchemes`-объявление остаётся чисто описательным: генератор `spring` не
создаёт по нему проверку.

### D6. Сборка в этом окружении

Целевой вариант — собственный Maven: скачать `apache-maven-3.9.x` в каталог `.tools/` (вне
`service/`), собирать JDK 16 из `~/.jdks` с `JAVA_HOME`, указанным для команды. Генератор
`spring` по умолчанию выпускает Spring Boot 2.7 и Java 8-совместимый код, поэтому JDK 16
достаточно; `useSpringBoot3` не включаем.

Если сборка на JDK 16 окажется несовместимой, эскалация к пользователю: установить JDK 17 +
Maven или подтвердить, что `mvn package` проверяется на его машине. Молча подменять
инструменты не будем.

## Risks / Trade-offs

- **Регенерация затирает рукописный код** → рукописные файлы лежат только в пакете `service`
  с именами, которых генератор не создаёт (`HabitStore`, `HabitService`, `HabitController`,
  `HabitAuthFilter`, `ApiExceptionHandler`); контроллер реализует сгенерированный интерфейс, а
  не дублирует его. После любого `generate` проверяем `git status` и `mvn package`.
- **Нет Maven/JDK 17** → см. D6; до подтверждения сборки задача остаётся незакрытой.
- **`400` вне контракта** → описано в D4/D2; `README.md` фиксирует расхождение явно.
- **Статический токен — не безопасность** → явная пометка в `README.md`, что это заглушка.
- **`total` в `HabitListResponse` может расходиться с фактическим содержимым** → `total`
  считается из отфильтрованной коллекции в одном месте, в `HabitService`.
- **Генератор может добавить свои `200`-модели и дефолтные заглушки** (`notImplemented`) →
  ручные реализации возвращают реальные данные, ни один метод интерфейса не остаётся
  заглушкой; проверяется при `mvn package` и ручным запросом.
