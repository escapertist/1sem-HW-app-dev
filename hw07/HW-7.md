## Задание 1
Карта зависимостей StPlatform (обязательная): код платформы нашего курса открыт — https://gitverse.ru/UnMatty/StPlatform. Найдите классы-слои (контроллеры/сервисы/репозитории — что там есть), протрассируйте одну функцию по рецепту субботы («сдать домашку», «регистрация»): Файл.метод → Файл.метод → … — и ответьте: все ли стрелки идут «вниз»? где провели бы границу иначе? зачем нужна эта граница (одной фразой)?

## Результат 1
### Классы-слои
Структура - классические 4 слоя + гейты и адаптеры: контроллеры (вход), Сервисы (правила), Репозитории (данные), Домен, Адаптеры (порты наружу), Сквозные гейты. Пакеты по фичам, а не по слоям, поэтому слой приходится читать по аннотации, а не по каталогу. DTO-слоя нет.

### Трассировка
Попробовала протрассировать "регистрацию". Открытой регистрации нет: это три операции — заведение + приглашение, согласия, пароль по токену.

TeacherImportController.importList → UserService.importStudents → importStudent → UserRepository.save → invite (токен) → InviteMailer.sendInvites. Затем ActivateController → ActivationService.invitedByToken → ConsentService → ConsentRecordRepository.save; ActivateController.setPassword → ActivationService.activate → PasswordEncoder → UserRepository.save. REST: ApiAuthController.activate → тот же ActivationService.activate.

### Ответ на вопрос "Все ли стрелки «вниз»?"
Да, по слоям - вниз. Но на регистрации три отклонения: контроллер сам оркестрирует ActivationService и ConsentService (шаг-машина в веб-слое), правило "пароль после согласия" продублировано в сервисе и контроллере, транзакция и письма разъехались (импорт коммитит, контроллер шлёт после), хотя есть готовый механизм событий после коммита.

### Граница иначе
Одна граница вместо трёх: "операция регистрации = один метод одного сервиса = одна транзакция", побочные эффекты - только событиями после коммита.

### Зачем нужна эта граница
Чтобы правило "приглашение = токен в БД + письмо строго после коммита" и "пароль строго после согласия" существовало в одном месте на оба входа (веб и API), а не в контроллерах, где его уже пришлось продублировать и где его легко обойти третьим входом.


## Задание 2
Та же трассировка для PetClinic («добавление визита», начать с VisitController) через агента. Результат текстом, с указанием агента и модели.
Критерий: список слоёв + цепочка вызовов + фраза «зачем граница».

## Результат задания 2
### Классы-слои
Слои: 6 контроллеров, web-инфраструктура (PetTypeFormatter, PetValidator, i18n, шаблоны), сервисного слоя нет, 3 репозитория Spring Data, 9 домен-сущностей (они же view-model), конфиг/кэш и SQL-ресурсы.

### Трассировка
Цепочка: VisitController.loadPetWithVisit → OwnerRepository.findById → Owner.getPet → new Visit() → Pet.addVisit → VisitController.processNewVisitForm → Owner.addVisit → Owner.getPet → Pet.addVisit → OwnerRepository.save → Hibernate cascade → INSERT visits → OwnerController.showOwner → OwnerRepository.findById → ownerDetails.html.

### Ответ на вопрос "Все ли стрелки «вниз»?"
Вниз ли: по зависимостям да, но есть четыре отклонения — бизнес-правило «визит только в будущее» в контроллере, view читает сущности напрямую, чтение из @ModelAttribute мимо хендлера (две транзакции), controller → repository без сервиса.

### Граница иначе
VisitService.bookVisit(ownerId, petId, visit) под @Transactional - одна транзакция на вариант использования, правило в домене, @ModelAttribute кладёт DTO, @Transactional/@Cacheable уходят из репозитория в сервис.

### Зачем нужна эта граница
Чтобы «записать визит» было одной атомарной операцией с одним местом для бизнес-правил, а веб-слой и БД можно было менять по отдельности.
