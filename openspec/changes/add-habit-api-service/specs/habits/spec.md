# Spec Delta

## Purpose

HTTP-управление привычками: клиент получает список своих привычек с фильтром по активности,
читает одну по идентификатору, создаёт, обновляет и удаляет их, получая предсказуемые коды
ответа и машиночитаемое тело ошибки.

## ADDED Requirements

### Requirement: Список привычек

Система SHALL возвращать по `GET /habits` коллекцию привычек вызывающего пользователя в теле
`HabitListResponse` с кодом 200. Необязательный query-параметр `active` SHALL фильтровать
коллекцию по признаку активности. Отсутствие подходящих привычек MUST давать пустой список, а не
ошибку.

#### Scenario: Полный список

- **WHEN** клиент вызывает `GET /habits` без параметров
- **THEN** сервис отвечает 200 и `HabitListResponse` со всеми привычками вызывающего

#### Scenario: Только активные

- **WHEN** клиент вызывает `GET /habits?active=true`
- **THEN** в ответе только привычки с `active = true`

#### Scenario: Только неактивные

- **WHEN** клиент вызывает `GET /habits?active=false`
- **THEN** в ответе только привычки с `active = false`

#### Scenario: Пустой результат

- **WHEN** у вызывающего нет привычек, удовлетворяющих фильтру
- **THEN** сервис отвечает 200 и пустым `items`

### Requirement: Чтение привычки

Система SHALL возвращать привычку по `GET /habits/{habitId}` с кодом 200 и телом `Habit`. Если
привычки с таким идентификатором не существует, ответ MUST быть 404 с телом `Error`.

#### Scenario: Привычка найдена

- **WHEN** клиент запрашивает `GET /habits/{habitId}` для существующей привычки
- **THEN** сервис отвечает 200 и `Habit` с этим идентификатором

#### Scenario: Привычка не найдена

- **WHEN** клиент запрашивает `GET /habits/{habitId}` для несуществующего идентификатора
- **THEN** сервис отвечает 404 и `Error` с осмысленным `message`

### Requirement: Создание привычки

Система SHALL создавать привычку по `POST /habits` из тела `HabitInput` и возвращать 200 с
созданным `Habit`. Сервис MUST присвоить новый идентификатор и заполнить поля, которых нет во
входных данных: `id`, владельца и метки времени. Если `active` во входных данных не передан,
привычка SHALL считаться активной.

#### Scenario: Создание с полным телом

- **WHEN** клиент отправляет `HabitInput` с `title`, `description` и `active = false`
- **THEN** сервис отвечает 200 и `Habit` с новым `id`, переданными значениями и `active = false`

#### Scenario: Значение активности по умолчанию

- **WHEN** клиент отправляет `HabitInput` без поля `active`
- **THEN** созданная привычка имеет `active = true`

#### Scenario: Созданная привычка видна в списке

- **WHEN** клиент создаёт привычку и затем вызывает `GET /habits`
- **THEN** созданная привычка присутствует в ответе списка

### Requirement: Обновление привычки

Система SHALL заменять поля привычки по `PUT /habits/{habitId}` значениями из тела `HabitInput` и
возвращать 200 с обновлённым `Habit`. Для несуществующего идентификатора ответ MUST быть 404 с
телом `Error`. Идентификатор и владелец привычки при обновлении MUST NOT изменяться.

#### Scenario: Успешное обновление

- **WHEN** клиент отправляет `HabitInput` с новым `title` для существующей привычки
- **THEN** сервис отвечает 200 и `Habit` с новым `title`, прежними `id` и владельцем

#### Scenario: Обновление несуществующей привычки

- **WHEN** клиент отправляет `PUT /habits/{habitId}` для несуществующего идентификатора
- **THEN** сервис отвечает 404 и `Error`

### Requirement: Удаление привычки

Система SHALL удалять привычку по `DELETE /habits/{habitId}` и возвращать 200 без тела ответа.
Для несуществующего идентификатора ответ MUST быть 404 с телом `Error`. После успешного удаления
обращение к тому же идентификатору MUST давать 404.

#### Scenario: Успешное удаление

- **WHEN** клиент удаляет существующую привычку
- **THEN** сервис отвечает 200 без тела, а последующий `GET /habits/{habitId}` даёт 404

#### Scenario: Удаление несуществующей привычки

- **WHEN** клиент отправляет `DELETE /habits/{habitId}` для несуществующего идентификатора
- **THEN** сервис отвечает 404 и `Error`

### Requirement: Формат тела ошибки

Любой ответ с кодом 401, 403 или 404 MUST содержать тело `Error` с непустым `message`,
пригодным для чтения человеком, и кодом состояния в поле `status`.

#### Scenario: Ошибка содержит код и сообщение

- **WHEN** сервис отвечает на запрос с кодом 404
- **THEN** тело содержит `status = 404` и непустой `message`

#### Scenario: Ошибка доступа содержит код и сообщение

- **WHEN** сервис отвечает на запрос с кодом 401 или 403
- **THEN** тело содержит `status` с этим кодом и непустой `message`
